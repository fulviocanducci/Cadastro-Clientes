# Architecture — Customer Registration

## 1. Overview

The project is a frontend-only customer registration application built with HTML, vanilla JavaScript, and Tailwind CSS v4.

The architecture must remain simple, maintainable, and ready for future integration with an ASP.NET Core backend, Entity Framework Core, and MySQL.

The current version must not include a backend, database, or persistent storage.

## 2. Technology Stack

### Current Version

- HTML5 for page structure.
- Vanilla JavaScript for form behavior and validation.
- Tailwind CSS v4 for styling.
- Tailwind CSS CLI for compiling CSS.
- ViaCEP API for Brazilian address lookup.
- Nunito Sans for typography.

### Future Backend

- ASP.NET Core for HTTP endpoints and server-side processing.
- Entity Framework Core for data access.
- MySQL for persistent customer records.

Future technologies must not be implemented until explicitly requested.

### File Responsibilities

- `AGENTS.md`: Instructions and constraints for AI-assisted development.
- `README.md`: Project overview, prerequisites, and commands.
- `package.json`: Dependencies and development/build scripts.
- `index.html`: Semantic HTML structure of the registration page.
- `src/input.css`: Tailwind CSS entry point and theme configuration.
- `src/js/app.js`: Form behavior, validation, masks, CEP lookup, and submission feedback.
- `docs/REQUIREMENTS.md`: Functional and non-functional requirements.
- `docs/DESIGN.md`: Visual identity, layout, responsiveness, and accessibility.
- `docs/ARCHITECTURE.md`: Technical structure and future integration guidelines.
- `public/css/styles.css`: Generated CSS output. Do not edit this file manually.

## 4. CSS Build Process

Tailwind CSS must be compiled locally using Tailwind CSS v4 and its CLI.

The source file is `src/input.css`.

The generated stylesheet is `public/css/styles.css`.

The build process must scan the HTML and JavaScript files for Tailwind utility classes.

The application must reference the generated stylesheet from `index.html`.

Production use must not depend on the Tailwind CDN.

## 5. JavaScript Responsibilities

The JavaScript module must handle:

- CPF and CNPJ input masks.
- CPF and CNPJ validation.
- Conditional validation of Company Legal Name.
- Email validation.
- Required field validation.
- CEP lookup through ViaCEP.
- Address field population.
- Validation and success messages.
- Form reset after successful submission.

Keep the implementation organized into small, focused functions.

Avoid unnecessary dependencies and global variables.

Do not introduce a frontend framework.

## 6. External API Integration

ViaCEP is the only external API used by the current application.

The application must handle:

- Valid CEP responses.
- CEPs that are not found.
- Network failures.
- Invalid CEP input.
- Manual address entry when the lookup fails.

The address lookup must not prevent the user from completing the form manually.

No customer registration data may be sent to ViaCEP.

## 7. Form Submission Flow

The current submission process is entirely client-side:

1. The user fills in the form.
2. JavaScript validates the fields.
3. If validation fails, the relevant messages are displayed.
4. If validation succeeds, a success message is displayed.
5. The form is reset.

This flow is demonstrative only. It must not claim that customer information has been saved.

## 8. Future Backend Integration

When backend integration is approved, the application may be extended to use ASP.NET Core endpoints.

The intended flow will be:

1. The user submits the form.
2. The frontend sends the customer data to an ASP.NET Core endpoint.
3. The backend validates the submitted data.
4. Entity Framework Core persists valid records in MySQL.
5. The backend returns an appropriate response.
6. The frontend displays the result.

Server-side validation must be implemented even when client-side validation already exists.

The frontend must not connect directly to MySQL.

The current implementation must not create placeholder endpoints, fake API calls, or database persistence.

## 9. Maintainability and Scope

- Keep filenames, identifiers, variables, and functions in English.
- Keep user-facing messages in Brazilian Portuguese.
- Use semantic HTML and accessible form controls.
- Prefer simple solutions over unnecessary abstractions.
- Keep generated files separate from source files.
- Avoid adding dependencies without a clear requirement.
- Follow `AGENTS.md`, `REQUIREMENTS.md`, and `DESIGN.md`.
- Resolve conflicting requirements before implementing changes.

## 10. Verification

Before considering the implementation complete:

- Verify that the Tailwind CSS build succeeds.
- Confirm that the generated stylesheet is referenced correctly.
- Test all form validation rules.
- Test successful submission and form reset.
- Test CEP lookup and manual address entry.
- Test mobile, tablet, and desktop layouts.
- Verify keyboard navigation and visible focus indicators.

Report any checks that could not be performed.
